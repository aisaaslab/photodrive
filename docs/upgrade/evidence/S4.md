# Sprint 4 · evidence

## S4-01 · sign-up date (`createdAt`) no longer reset (2026-11-26, SEC-4)

**The bug.** `upsertUser` (run at every sign-in) wrote `createdAt: serverTimestamp()` each time, so a profile's `createdAt` was always the user's last sign-in. The admin "Joined" column was unaffected (it reads Firebase Auth's creation time), but the Firestore field was wrong for anything that uses it.

**The fix (code, no data touched).**
- `lib/firestore/profile-write.ts` (pure): `createdAt` is included only when the profile has none. `name` and `photoURL` behave as before (written only when nothing is stored).
- `firestore.rules`: a signed-in user can no longer change `createdAt` on their own profile (create is unchanged). So even an old cached copy of the app cannot reset it.
- `components/auth/AuthProvider.tsx`: the sign-in upsert is wrapped in try/catch, so a refused write (an old cached client after the rules change) never breaks sign-in.
- **Order of rollout:** deploy the app first, then publish the rules (the owner does that, `firebase deploy --only firestore:rules`). In the other order, the old app's sign-in write is refused until it is replaced. Nothing breaks either way (the upsert is non-fatal), but the date would not be refreshed.

**The data repair (script, dry run first, NOT yet run on any real project).** `scripts/migrations/restore-created-at.ts` compares each `users/{uid}.createdAt` with Firebase Auth's creation time.
- A date is moved **earlier only**, and only when it is more than one day later than Auth's (the first profile write follows account creation within seconds, so anything inside a day is genuine). Dates earlier than Auth's (imported accounts) are never moved. A missing date is filled.
- The new value keeps the **type already stored** (Firestore Timestamp stays a Timestamp, a number stays a number), because the admin-created profiles use `Date.now()` and the browser-created ones a Timestamp.
- Only the `createdAt` field is written, in batches of 400; re-running finds nothing left to do. Profiles with no Firebase Auth account are reported and left alone.
- Dry run by default, prints the project first, writes a JSON report (every user, current date, restored date). `--apply` refuses to run without `--out`: the report with all previous values is written **before** anything changes, so it can be undone.
- Run (owner, production credentials; nothing here has ever pointed at production):
  `npx tsx --env-file=.env.local scripts/migrations/restore-created-at.ts --out report.json` and review `report.json`; then add `--apply`.

**Tests.** `tests/profile-write.test.ts` (5), `tests/security/created-at.emu.test.ts` (8): signing in twice through the real client SDK against the real rules leaves `createdAt` unchanged; the old write is refused by the rules; other profile fields are still editable; the migration plan (types, tolerance edge cases, missing, no Auth account), apply (only `createdAt` written, types kept, second run empty, 450 documents across batches).

**Status:** code done and tested; the task stays *in progress* until the owner has reviewed the production dry-run report (its "done when").

## S4-02 · cascade deletes (2026-11-26, SEC-4)

**The problem.** A gallery's client favourites live in `gallery_selections/{galleryId}` together with the client's submission (name, e-mail, note). Three paths delete galleries (the owner's delete, a user deleting their own account, an admin deleting a user) and none removed that document, so it stayed forever, including a third party's e-mail address.

**The change.** `lib/server/repos/galleries.ts` is now the one place that knows what belongs to a gallery: `deleteGalleryCascade`, `deleteGalleriesCascade`, `deleteUserGalleries`. All three routes use it. It removes `gallery_selections/{id}`, any legacy `favorites` documents with that `galleryId` (nothing writes them any more, rules deny clients, but they may exist), and then the gallery.
- **Children first, gallery last:** if something fails part-way the gallery is still there and the deletion can simply be repeated; the other order would leave orphans that nobody can find. (Tested by making the first batch fail.)
- Batches of 400 writes; legacy lookups in groups of 30 (Firestore's `in` limit). Ids that do not exist are fine.
- Account deletion previously deleted the profile in the same batch as the galleries; it now deletes the galleries (cascade) and then the profile, and Auth afterwards as before. Payments are kept on purpose (accounting), as the existing comment says.

**Tests.** `tests/security/cascade-delete.emu.test.ts` (8): the cascade removes exactly one gallery's data and leaves another's; missing ids; 450 galleries across batches; failure leaves the gallery; the three routes (including that another user's gallery cannot be deleted and keeps its favourites); and a final "no orphaned selection documents" check.

**Not done (parking lot):** selections orphaned by deletions that happened *before* this change are still in production. A dry-run-first sweep (list `gallery_selections` whose gallery no longer exists, report, then delete) would clean them; it needs the owner's go-ahead like the other data scripts. Added to the S4 parking lot.

## S4-03 · Firestore rules: every server-only field locked, with tests (2026-11-26, SEC-7)

- **The gap.** `locked()` listed six fields. The server also writes `planId`, `planName`, `planInterval`, `subscriptionSource`, `promoCode` (and, from the reminder features, `remindersSent`), and a signed-in browser could write all of them to its own profile. They do not grant access (the access fields were already locked), but they are what the admin Users page and the Account page display, so a user could relabel their own plan, source and promo code.
  Proved with the new tests against the **old** rules: exactly those six fail, the other 23 pass.
- **The fix.** `firestore.rules` `locked()` now lists all twelve server-only fields (documented one by one in the file). The stale "Galleroo" header became "PhotoDrive". (`createdAt` is protected separately since S4-01.)
- **Not locked on purpose: `email` and `uid`.** The sign-in upsert writes them (unchanged values are not a change, so that still works). Payment-to-account matching uses Firebase Auth's `getUserByEmail`, not the profile's e-mail field, so editing it cannot redirect a payment.
- **Tests: `tests/rules/firestore-rules.emu.test.ts` (30)**, run by `npm run test:emu` in CI:
  - for each of the twelve fields: cannot be created, added (update and merge-set), changed or removed by the owner of the profile;
  - a whole-document overwrite that drops or changes a locked field is refused; writing a locked field back with the same value is allowed (a normal save);
  - what still works: creating one's own profile, editing name/photo, reading one's own profile; not another user's profile, no listing, no anonymous access, no deleting a profile;
  - all other collections (galleries with their passwords, selections, favourites, payments, plans, Stripe events, notices, contact messages, demos, settings, and an unknown one) deny every read, write and delete for signed-in and anonymous users, and cannot be listed;
  - a guard test fails if `locked()` and the test's field list drift apart.
- **Rollout:** publishing rules is an owner action (`firebase deploy --only firestore:rules`); this session does not do it. Server code (Admin SDK) is unaffected by rules.

## S4-04 · legacy plaintext passwords: one-off migration, reads no longer write (2026-11-26, SEC-8)

**Before.** Old galleries stored the password in plaintext (`password`) next to the bcrypt hash. Newer code stores it sealed (`passwordEnc`, AES-256-GCM, key derived from `GALLERY_JWT_SECRET`). Old plaintext was sealed lazily, by the owner's gallery list, the admin gallery list and the admin users list: three **read** endpoints that wrote to Firestore.

**Now.**
- `lib/server/migrations/seal-legacy-passwords.ts` + `scripts/migrations/seal-legacy-passwords.ts`: dry run by default, prints the project, `--out report.json` (required for `--apply`). Every plaintext copy is cleared. For each gallery:
  - **seal_and_clear**: no sealed copy and the plaintext verifies against the bcrypt hash (it is the live password): sealed, then cleared, so the owner's "remind me" still works;
  - **clear_only**: a sealed copy already exists (it wins), or the plaintext cannot be verified (no hash, or it does not match the hash, so it is not what visitors need): cleared, no reminder created. Each item carries a note saying which and why.
- **No password in any report or log**, and no sealed value either (tested by searching the report text for every seeded secret).
- **Safe to re-run and to run while owners edit:** each gallery is re-read in a transaction and skipped if its plaintext is no longer the planned one (an owner who changed the password meanwhile is never overwritten). Visitors are never affected (they are checked against the hash, which is not touched).
- **The three read endpoints no longer write** (`migrateLegacyPassword` is deleted). `forOwner` still shows a legacy plaintext password to its owner until the script has run. A test reads all three endpoints and checks every gallery document is unchanged. (The only other `GET` handler with a `.set(` is a `Map` in promo codes, not Firestore.)
- Tests: `tests/security/seal-legacy-passwords.emu.test.ts` (4): plan per case, report without secrets, apply (seals the verified one, the sealed copy wins, unverified plaintext is dropped, second run empty), the changed-meanwhile race, and the no-writes-on-read check.

**Run order for the owner (production).** 1) Deploy this code. 2) Dry run: `npx tsx --env-file=.env.local scripts/migrations/seal-legacy-passwords.ts --out report.json` and read the report (counts, per-gallery notes). **`GALLERY_JWT_SECRET` in that environment must be the production value** (it derives the sealing key; the script refuses to run without one). 3) After approval, the same command with `--apply`; it prints "Plaintext passwords remaining: 0".
Until step 3, legacy plaintext stays where it was (the lazy clean-up no longer runs), so do it soon after the deploy.

**Status:** code done and tested; stays *in progress* until the production report shows zero plaintext left (its "done when").

## S4-08 · `server-only` on every server module (2026-11-26, SEC-9)

- **What is guarded (42 modules):** every file under `lib/server/**`, plus the server helpers that live elsewhere: `lib/email.ts`, `site-settings.ts`, `plans.ts`, `promo-codes.ts`, `tracking-settings.ts`, `stripe/activate.ts`, `firebase/admin.ts`, `firebase/admin-guard.ts`, `drive/client.ts`, `gallery/password.ts`, `gallery/session.ts`, `gallery/password-vault.ts`. Each starts with `import "server-only";`.
- **Found by the build while doing it:** the client-side subscribe page imported pure access-date helpers from `lib/server/billing/access.ts`. That module has no server dependencies, so it moved to `lib/shared/billing-access.ts` (all imports and docs updated). The rule is now simple: nothing under `lib/server/` is ever shared with the browser.
- **No new dependency.** Next recognises the `server-only` import by name and resolves it itself (the Next docs say installing the package is optional), so none was added. Outside a Next build the real package would throw, so `tsconfig.json` (used by `tsx` for the maintenance scripts) and both Vitest configs map the specifier to an empty module, `lib/shims/server-only.ts`.
  (An attempt to install the package was declined by the session's permission system, so this route was taken instead; it can be switched to the package later by deleting the shim and the two aliases.)
- **Done when "an accidental client import fails the build": shown, not assumed.**
  1. With the alias in place, a Client Component that imported a guarded module made `next build` fail: *"'server-only' cannot be imported from a Client Component module"* (experiment, reverted).
  2. `tests/server-only-guard.test.ts` (4 tests, runs in CI) checks all 42 modules carry the guard and walks the import graph from **every** `"use client"` file; it fails with the whole chain (e.g. `PhotoTile.tsx -> lib/zz-helper.ts -> lib/server/http.ts`), which I confirmed with a temporary indirect import, then reverted.
  3. CI's `next build` is the real gate, as in (1).
- **Nothing broke at runtime:** the production build compiles; all 214 unit and 362 emulator tests pass with the guards; the maintenance scripts still run under `tsx` with no new flags (verified with a probe); and the real-browser protected-tier check (19 checks) passes against a production server built with the guards.
- Lint stays at 13 warnings.

## S4-05 · one Stripe customer per user (2026-11-26, PAY-5)

**Before.** Checkout was given only `customer_email`, so each purchase left Stripe with a separate guest record: no history per person, no invoices tied to a customer (S4-06 needs one), nothing to hang saved payment methods on.

**Now, only when `BILLING_FULFIL_V2` is on** (the live shop is unchanged until then; tested):
- `lib/server/billing/customer.ts` `ensureStripeCustomer(stripe, db, user)` finds or creates the user's Stripe Customer once and keeps its id on `users/{uid}.stripeCustomerId`; checkout passes `customer` instead of `customer_email` (Stripe does not allow both; the receipt goes to the customer's e-mail).
- **No duplicates, in order:** 1) a stored id is reused if Stripe still has it (and an untagged old one is tagged with the uid); 2) else search Stripe by `metadata.uid` (finds a customer created before its id was saved); 3) else create with an **idempotency key** per user, so simultaneous checkouts get the same customer; 4) store the id **only if none was stored meanwhile** (transaction), and the stored one wins.
- **Edge found by the tests:** Stripe replays an idempotency key for 24 hours, which would hand back the customer being replaced (a customer deleted in the dashboard, or an id from the other Stripe mode). The replaced id is part of the key.
- **Deliberately not matched by e-mail:** customers from earlier Checkout sessions have no `metadata.uid`, and two people can share one address, so a user without a stored id gets a new Customer rather than adopting a stranger's.
- **Never blocks a payment:** if the customer lookup or creation fails, checkout falls back to today's behaviour (`customer_email`, guest) and logs a warning.
- Tests: `tests/billing/stripe-customer.emu.test.ts` (12) with an in-memory Stripe Customers fake that models idempotency keys, `resource_missing`, deleted customers and `metadata['uid']` search (`tests/helpers/stripe.ts`): first purchase creates one and checkout uses `customer`; **second and third purchases reuse the same customer**; users are separate; three simultaneous checkouts make one customer; Stripe failure falls back to e-mail; flag off = no customer calls at all; reuse/tagging, replacement of unknown or deleted ids, adoption by uid, no adoption of other users' or same-e-mail customers, the lost race, and a quote in a uid cannot alter the search query. The existing checkout tests now use the fake too (no network).

**Status: in progress.** The "done when" holds in tests, but the plan requires payment changes to be proved in Stripe **test mode** first. That needs the staging environment (D12, deferred): create a customer, buy twice, check one Customer with two payments in the dashboard, and that `customers.search` by `metadata['uid']` finds it (search is eventually consistent by up to about a minute; that is why creation is also idempotent).

## S4-07 · local payment methods and delayed payments (2026-11-26, PAY-5)

Only with `BILLING_FULFIL_V2` on; the live shop (flag off) stays card-only, as before (tested).

- **Checkout** (`app/api/stripe/checkout/route.ts`): with the flag on, `payment_method_types` is no longer pinned to `card`. Stripe shows the methods enabled in the dashboard that suit the customer's country and the plan's currency (iDEAL, Bancontact, SEPA Debit, Klarna ... as the owner chooses). No code change is needed to add or remove a method.
- **Delayed methods** (SEPA Debit, transfers): the session completes with `payment_status: "unpaid"`; the existing fulfilment path (S1/S2) already ignores unsettled sessions and fulfils on `checkout.session.async_payment_succeeded` (idempotent); `async_payment_failed` produces the failure notice (S2-14). New in this task: the **thank-you page tells the customer** instead of treating it as a problem.
  `POST /api/stripe/verify` now returns `awaiting: true` when the session is complete but unpaid (not when still open, expired or paid); the page shows "Payment on its way" (six languages, **draft wording, native review needed**) with links to the dashboard and account, and stops polling.
- **Tests** (all added to existing suites): the checkout does not pin methods (flag on) and still pins `card` (flag off); `awaiting` only for complete-and-unpaid; **a delayed payment end to end**: verify says awaiting and grants nothing, then a signed `async_payment_succeeded` webhook grants the plan's access, then verify says paid and already fulfilled. i18n key parity passes with the two new keys.
- **Known limit, in the docs:** the conversion pixel fires only for payments already paid when the page loads, so a delayed payment is not reported as a purchase.
- **Dashboard steps for the owner:** `docs/upgrade/04-environments-testing-release.md` > "Stripe dashboard checklist for local payment methods" (enable the methods; subscribe the webhook to the two async events; EUR plans for most local methods; keep Stripe's receipts on).

**Status: in progress.** The "done when" (an iDEAL and a SEPA test payment complete and activate access) needs Stripe **test mode** and the dashboard settings above: staging (D12, deferred) plus the owner's choice of methods. Everything that can be proved without Stripe is.
