## S7-02 · Roles: more than one administrator (2026-11-27)
- **What changed.** An administrator is the bootstrap account named by `ADMIN_UID`, or any user with the Firebase custom claim `admin: true` (`isAdminToken`, `requireAdmin` in `lib/server/auth.ts`). All 15 admin route files now use `requireAdmin` (it answers 401 without a valid token and 403 for a signed-in non-administrator; before, both were 403), and the four other places that special-cased the administrator (the paywall skip when creating a gallery, "admin doesn't pay" in the subscription and payments answers, and the right to fetch any gallery's originals) use the token check too.
- **Revocation works at once.** A claim is honoured only after the token is checked against Firebase Auth's revocation list (`verifyIdToken(token, true)`), so revoking an administrator does not wait for their one-hour token to expire. The bootstrap account needs no claim and no extra check.
- **Granting and revoking:** `npx tsx --env-file=.env.local scripts/admin/set-admin-claim.ts grant|revoke <email-or-uid> [--apply]`. Dry run by default; prints the project first; keeps the user's other claims; revoke also revokes their refresh tokens; each change writes an audit entry. A granted user signs in again to get the role. (The owner runs this with production credentials; nothing was run against production.)
- **Proof.** Unit tests (`tests/auth.test.ts`, 5 new): the claim must be exactly `true`, a claim user triggers the revocation check, a revoked one is 403, no claim means no extra network call, the bootstrap account is unchanged. Emulator tests (`tests/security/admin-roles.emu.test.ts`) against the real Auth emulator: a normal user is refused, a dry run writes nothing, after a grant and a fresh sign-in the user gets 200 from an admin route, after a revoke the old token and a fresh sign-in are both refused, other claims survive, a uid works as well as an e-mail, double grants change nothing. The emulator also invalidates older tokens when claims change (401), so the revocation path itself is pinned by the unit tests.
- Four older emulator tests mocked the old helper; they now authenticate through the token verifier like the real routes.

## S7-03 · Audit log (2026-11-27)
- `lib/server/audit.ts`: `writeAudit({ actorUid, action, targetType, targetId, before?, after?, note? })` appends to `audit_log` (same shape the back-fill already used). Secrets are never stored (any field named like a password, hash, token or secret is replaced by "[redacted]"), `undefined` is dropped, and it never throws: a failed write is logged at error level and does not undo an action that already happened. Firestore rules deny all client access to the collection.
- **Wired into every admin mutation:** plan create / toggle / update / delete; user create and delete; subscription assign plan, grant lifetime, grant year, revoke (before and after of the user's access); gallery update and delete; site settings update; promo code create / update / delete; support message read/unread and delete (the visitor's name and e-mail are deliberately not copied); admin grant and revoke.
- **Proof.** 5 unit tests (`tests/audit.test.ts`) and 3 emulator tests: each plan action leaves an entry with the actor, target and before/after (price 9900 to 12000 and so on); a subscription grant records the user's access before and after; promo and gallery changes are audited and a gallery's password hash never appears; user create/delete and message delete are audited without personal data; a refused request (not an administrator) writes nothing. 396 emulator tests and 344 unit tests pass; lint at 13 warnings.
- Not covered by an emulator test: the site-settings audit (that route calls `revalidateTag`, which only works inside Next); it is a three-line addition next to the covered ones.
