# S7 evidence: admin back office foundation

## S7-01 · superseded
By decision D9 (2026-11-26) the admin area, like the rest of the user area, is designed in code on the Concept B tokens and primitives instead of in Figma. The information architecture in the S7 sprint file (Overview, Users with a detail drawer, Galleries, Payments with Needs attention, Support, Plans and promo codes, Settings) is the brief; the screens are built in S7-05/06 and S8.

## S7-02 · Roles: more than one administrator (2026-11-27)
- **What changed.** An administrator is the bootstrap account named by `ADMIN_UID`, or any user with the Firebase custom claim `admin: true` (`isAdminToken`, `requireAdmin` in `lib/server/auth.ts`). All 15 admin route files now use `requireAdmin` (it answers 401 without a valid token and 403 for a signed-in non-administrator; before, both were 403), and the four other places that special-cased the administrator (the paywall skip when creating a gallery, "admin doesn't pay" in the subscription and payments answers, and the right to fetch any gallery's originals) use the token check too.
- **Revocation works at once.** A claim is honoured only after the token is checked against Firebase Auth's revocation list (`verifyIdToken(token, true)`), so revoking an administrator does not wait for their one-hour token to expire. The bootstrap account needs no claim and no extra check.
- **Granting and revoking:** `npx tsx --env-file=.env.local scripts/admin/set-admin-claim.ts grant|revoke <email-or-uid> [--apply]`. Dry run by default; prints the project first; keeps the user's other claims; revoke also revokes their refresh tokens; each change writes an audit entry. A granted user signs in again to get the role. (The owner runs this with production credentials; nothing was run against production.)
- **Proof.** Unit tests (`tests/auth.test.ts`, 5 new): the claim must be exactly `true`, a claim user triggers the revocation check, a revoked one is 403, no claim means no extra network call, the bootstrap account is unchanged. Emulator tests (`tests/security/admin-roles.emu.test.ts`) against the real Auth emulator: a normal user is refused, a dry run writes nothing, after a grant and a fresh sign-in the user gets 200 from an admin route, after a revoke the old token and a fresh sign-in are both refused, other claims survive, a uid works as well as an e-mail, double grants change nothing. The emulator also invalidates older tokens when claims change (401), so the revocation path itself is pinned by the unit tests.
- Four older emulator tests mocked the old helper; they now authenticate through the token verifier like the real routes.

## S7-03 · Audit log (2026-11-27)
- `lib/server/audit.ts`: `writeAudit({ actorUid, action, targetType, targetId, before?, after?, note? })` appends to `audit_log` (same shape the back-fill already used). Secrets are never stored (any field named like a password, hash, token or secret is replaced by "[redacted]"), `undefined` is dropped, and it never throws: a failed write is logged at error level and does not undo an action that already happened. Firestore rules deny all client access to the collection.
- **Wired into every admin mutation:** plan create / toggle / update / delete; user create and delete; subscription assign plan, grant lifetime, grant year, revoke (before and after of the user's access); gallery update and delete; site settings update; promo code create / update / delete; support message read/unread and delete (the visitor's name and e-mail are deliberately not copied); admin grant and revoke.
- **Proof.** 5 unit tests (`tests/audit.test.ts`) and 3 emulator tests: each plan action leaves an entry with the actor, target and before/after (price 9900 to 12000 and so on); a subscription grant records the user's access before and after; promo and gallery changes are audited and a gallery's password hash never appears; user create/delete and message delete are audited without personal data; a refused request (not an administrator) writes nothing. 396 emulator tests and 344 unit tests pass; lint at 13 warnings.
- Not covered by an emulator test: the site-settings audit (that route calls `revalidateTag`, which only works inside Next); it is a three-line addition next to the covered ones.

## S7-04 · Overview numbers without scanning (2026-11-27)
- **Before.** `GET /api/admin/stats` read every user, every gallery and every payment, and listed up to 1,000 Auth accounts, on every page view. It would have silently stopped counting at 1,000 users and its cost grew with the business.
- **Now.** `lib/server/repos/stats.ts`. Totals (users, new in 7/30 days, galleries, free-code sign-ups, paid payments) are Firestore aggregation queries (`count()`), revenue is `sum(amountTotal)` computed by the database per currency, and only the users whose access has not run out are read (six small fields each) to split monthly, yearly and comp and to list who expires within 30 days. Five recent sign-ups come from one ordered, limited query. Only the 15 people shown get their Auth profile looked up. The answer is stored in one document, `system_state/stats-overview`; the endpoint serves it while it is under ten minutes old and rebuilds it otherwise, and `/api/cron/stats-recompute` (nightly at 04:29 UTC, `CRON_SECRET`, `vercel.json`) rebuilds it regardless. No new Firestore index is needed (every filter is a single field or an equality).
- **Revenue per currency** (`revenueByCurrency`), never added across currencies; `revenueUsd` is kept for the existing page, which now lists other currencies next to it. Same definitions as before: active means status `active` and not expired, a $0 checkout is a free-code sign-up and not a payment.
- **Deliberate difference from the sprint text.** The sprint said "stored counters updated as things happen". Counters that every code path must remember to bump can drift. Recomputing from the database is always right, the cache bounds the cost, and the nightly job is the guarantee. Recorded here so it is not mistaken for an oversight.
- **Found on the way.** `users.createdAt` is a Firestore Timestamp for client writes and a number for restored profiles; a range query matches only its own type, so the sign-up counts query both. (S7-05 must handle the same.)
- **Proof.** `tests/security/stats.emu.test.ts` (8 tests, emulator): every number checked against a hand-worked dataset (three users in the last seven days counting both date types, a cancelled user with a future expiry is not active, an expired one is not active, lifetime access is not "expiring soon", a $0 and a no-amount payment are not payments), currencies are kept apart, an empty database works, the cache holds for ten minutes and then refreshes, a damaged document is replaced, the admin endpoint refuses non-admins, the cron needs the secret and refuses to run without one. 352 unit and 404 emulator tests pass, typecheck clean, lint at 13 warnings.
- Not done here: a read-count measurement against a large dataset (needs production data or a seeded load test); the design argues the cost (about 15 aggregation units plus the active users) and the emulator cannot price reads.

## S7-05 · Users: paged, searchable, filterable, with a detail drawer (2026-11-27)
- **Before.** `GET /api/admin/users` listed up to 1,000 Auth accounts and read every user, gallery and payment to build one answer; the page filtered and sorted all of it in the browser, so it silently stopped at 1,000 and got slower with every account.
- **API.** `GET /api/admin/users?q&filter&cursor&limit` (`lib/server/repos/admin-users.ts`). One indexed Firestore query per page (limit 1 to 50, default 25) with an opaque cursor. Search is an e-mail prefix on `emailLower` (case-insensitive). Filters: Everyone (A to Z), Active, Expiring within 30 days (lifetime never counts), Lapsed, Complimentary; with a search the filter is applied to the matches. Only the people on the page cost anything extra: one Auth lookup for the page, a gallery count and the newest gallery per person, one payment query for the page. The response carries `total` and `needsBackfill`. `GET /api/admin/users/[uid]` feeds the drawer: access, 20 newest payments, 20 newest galleries (the edit form's fields, never a password), and the last 15 audit entries about that user.
- **`emailLower`.** Written at every sign-in (`buildProfileWrite`), set on admin-created users, and the Firestore rules accept it only as the lower-cased form of the profile's own e-mail (so nobody can plant a value to appear under another address). Profiles created before are filled in by `scripts/migrations/backfill-email-lower.ts`: dry run by default, prints the project, writes a report with every previous value before changing anything, refuses `--apply` without `--out`, re-running is harmless. Until it has run, those people are missing from the list and search; the screen says how many ("N accounts are missing from this list…") instead of hiding them silently.
- **Indexes.** Three composite indexes added to `firestore.indexes.json` (users: subscriptionStatus + subscriptionExpiresAt, compGranted + emailLower; audit_log: targetId + at desc). Every other query uses single-field indexes or ones that already existed. **The emulator does not enforce indexes, so this is not proven here:** deploy them (`firebase deploy --only firestore:indexes`) before the first production use; Firestore names any missing index in its error.
- **Screen.** `/dashboard/admin/users`: search, filter chips with a one-line explanation, rows with a state badge (Active, Expiring soon, Lifetime, Lapsed, No plan) and a payment-issue flag, "Load more" and an end-of-list line, a retry on error, a count that is the real total. The detail drawer (`components/admin/UserDrawer.tsx`) holds the plan and end date, how they got access, assign plan, +1 year, free lifetime, revoke (with confirmation), payment issues with "Mark reviewed", payments, galleries (open, Drive folder, edit, delete) and what administrators did to this person; deleting a user needs their e-mail typed. All actions go through the existing audited endpoints. The old inline gallery editing was kept (now in the drawer); the one change is that an administrator can no longer read a client's gallery password, only set a new one or keep the current one.
- **Modal fix found on the way.** The dashboard's `<main>` is its own stacking context below the sticky header, so any modal inside it was painted under the header (a drawer's close button was unreachable by mouse). `Modal` now renders on `document.body` through a portal and gained `align="end"` for drawers. This touches every dashboard dialog: the dashboard behaviour snapshot (45 observations) is unchanged except that the dialog text of the two payment-step observations is now read from the dialog, not from the whole body (its DOM position moved), and the baseline was refreshed for that reason only.
- **Proof.** `tests/security/admin-users.emu.test.ts` (14 tests, emulator): walks 1,500 users in 30 pages, every one exactly once and in order (no ceiling); a page makes one Auth lookup for 25 people; page size is clamped; search by prefix in any case and through its pages; each filter matches the overview's definitions (cancelled with a future end is not active, lifetime is not expiring, revoked and never-subscribed are not lapsed); a filtered search still fills a page when most matches are filtered out; the row combines profile, Auth, galleries and payments and falls back to the profile without an Auth account; profiles without `emailLower` are counted and appear after the backfill, and the backfill is a no-op the second time; the endpoints refuse non-administrators (401/403), validate the filter and cursor, and the detail returns payments, galleries, activity and never a password; 404 for a stranger. Rules tests: `emailLower` is accepted only as the lower-cased own e-mail. Unit: sign-in write includes it. 345 unit and 419 emulator tests pass, typecheck clean, lint at 13 warnings.
- **Browser proof** (`scripts/verify/browser/admin-users.cjs`, production build on the emulators, 1,200 seeded profiles plus five named people; 30 checks, all pass): 25 rows on the first page; the header shows 1,207 accounts, not 1,000; "Load more" pages through to the end (1,206 rows); search finds one person in any case and says so when nobody matches; Expiring, Lapsed, Complimentary and Active show exactly the right people; the drawer shows plan, payment and both galleries with visibility; +1 year shows a message and an entry under "What administrators did"; a gallery can be renamed from the drawer; Escape closes it and focus returns to the row; a refunded payment is flagged on the row and "Mark reviewed" clears it; Delete stays disabled until the e-mail is typed and then removes the person; no horizontal scroll and the drawer fits at 390; **axe (WCAG 2.1 AA) clean on the list and the drawer at 1440 and 390**.
- **Owner actions before this goes live:** deploy the indexes and the rules; run the backfill (dry run, review the report, then `--apply`). The old page keeps working only until then in the sense that the screen warns about missing accounts; nothing else depends on it.
- **Not done here:** a 10,000-user timing run (the design reads a constant number of documents per page; the emulator cannot price reads; the 1,500-user walk and the 1,200-user browser run show no ceiling); the Galleries list and disable/enable are S7-06; the admin screens are not re-skinned yet beyond what this page needed (S8).
