# S3 evidence

## S3-01 · shared rate limiter (2026-11-25, SEC-2)

`lib/server/rate-limit.ts`. Nothing uses it yet: the routes are moved over in S3-05 (password lockout), S3-06 (contact and
selection-submit), S3-07 (demo limit) and S3-02/S3-04 (media). No new package: Upstash Redis is used through its REST API (decision D6).

- **Stores:** `UpstashStore` (production/staging; sends one atomic `/multi-exec` request per call: `INCR`, `EXPIRE … NX`, `PTTL`) and
  `MemoryStore` (local development and tests; bounded size). `getRateLimiter()` picks Upstash when `UPSTASH_REDIS_REST_URL` and
  `UPSTASH_REDIS_REST_TOKEN` are set, otherwise memory, and logs a warning once in production because memory limits are per
  server instance (the original SEC-2 defect).
- **`limit({ name, id, limit, windowSec })`:** fixed window starting at the first call; returns `allowed`, `remaining`, `retryAfterSec`.
  `rateLimitHeaders()` builds `RateLimit-*` and `Retry-After`.
- **Lockout** for password-style secrets: `isLocked` (check first), `recordFailure` (default 5 failures in 10 min lock for 15 min),
  `reset` (a correct secret clears the failure count but never lifts an active lock).
- **Privacy:** identifiers are hashed (`sha256`, optional `RATE_LIMIT_SALT`), so no raw IP is ever a Redis key; tested.
- **Client IP:** `clientIp()` prefers `x-vercel-forwarded-for` then `x-real-ip` (set by the platform, not forgeable by the client);
  the first `x-forwarded-for` entry is only a local-development fallback.
- **Failure mode:** if the store is unreachable the limiter fails **open** (the request goes through and an error is logged) so a Redis
  outage cannot take the site down; `failClosed: true` is available where denying is safer.

Tests: `tests/rate-limit.test.ts` (20). The Upstash tests run against an in-process fake server that speaks the same REST protocol, and
show: the exact commands and `Authorization` header sent; **limits hold across two separate limiter instances sharing the store**; a
lockout set by one instance is seen by the other; windows expire; HTTP errors, command errors and timeouts fail open (or closed on request).

**Needed for production:** create an Upstash Redis database and set the two environment variables in Vercel (D6). Until then limits stay
per instance. Not yet exercised against a real Upstash database (no credentials in this session).

## S3-05 · password verification hardened (2026-11-25, SEC-2, SEC-3)

`app/api/gallery/verify-password/route.ts`, using the S3-01 limiter (in-memory until Upstash is configured) and `zod` (new dependency).

- **Validation:** bad JSON or wrong/oversized fields (slug 1-200, password 1-200 characters) answer `400 {"error":"Invalid request"}` before any
  database access, and never count as a password attempt. (The 200-character cap also bounds bcrypt work.)
- **Lockout:** 5 wrong passwords within 10 minutes for the same visitor **and** gallery lock that pair for 15 minutes (`429`, `Retry-After: 900`);
  while locked even the right password is refused. A correct password clears the count. Another visitor, or the same visitor on another
  gallery, is unaffected. Guessing at galleries that do not exist locks the same way.
- **Per-IP limit:** 30 attempts per minute per IP across all galleries (stops one visitor trying many galleries).
- **Generic errors:** a wrong password, an unknown gallery and a gallery without a password all answer the identical `401 {"error":"Incorrect password"}`,
  and each costs one real bcrypt compare (a lazily created dummy hash is used when there is nothing to compare against), so neither the body nor
  the response time reveals which galleries exist.
- **Cookie:** `httpOnly`, `SameSite=Strict`, 7 days, **`Secure` when `NODE_ENV=production`**.
- **Visitor message:** the password gate showed "connection error" for anything but a 401; it now shows a proper "too many wrong attempts, wait a few
  minutes" message (`gallery.tooManyAttempts`, six languages, covered by the parity test; draft wording, needs native review).
- **IP source:** `clientIp()` (platform headers first). With no Upstash credentials the lockout is per server instance, so it is only fully effective once
  `UPSTASH_REDIS_REST_URL`/`TOKEN` are set in Vercel.

Tests: `tests/security/verify-password.emu.test.ts` (12, real Firestore emulator and real bcrypt) plus the i18n parity test. Not exercised in a browser.

## S3-13 · gallery visibility, public or private (D18) (implemented; copy review and browser check outstanding)

**Rule (owner, 2026-11-25):** every gallery is either **public** (no password, the link opens it) or **private** (a password is required). The
protected delivery of D15 (S3-02, S3-03) will key off this plus "downloads disabled".

**Code**
- `lib/gallery/visibility.ts` (pure, shared by server and browser): `galleryVisibility`, `isPrivate`, `planCreate`, `planUpdate`. The one rule set
  behind the owner and admin APIs; 16 unit tests, including an invariant check that no accepted update can leave a private gallery without a
  password source or give a public gallery one.
- **Existing galleries are derived, nothing is migrated:** a stored password means private, none means public. Fail safe: a gallery that has a
  password hash is *always* served as private, whatever its `visibility` field says (`isPrivate`). Owner and admin API responses now always carry
  `visibility`.
- **Create (`POST /api/galleries`):** `visibility: "private"` requires a password (400 `A private gallery needs a password`); `"public"` refuses one
  (400 `A public gallery cannot have a password`); the password is capped at 200 characters (what the unlock endpoint accepts). A client that sends no
  `visibility` behaves exactly as before (password = private, none = public). Bad JSON/shape now answers 400, not 500.
- **Edit (`PATCH /api/galleries/[id]` and the admin `PATCH /api/admin/galleries/[id]`):** same rules. A private gallery keeps its password when none is
  sent and can never lose it without becoming public (`removePassword` on a private gallery that stays private is refused); switching to public removes the
  password and bumps `pwChangedAt` (old unlock cookies stop working); public to private needs a new password. Older clients keep working
  (`removePassword` = public, a new password = private).
- **Gating:** the public gallery page, `download-all` and selection-submit now use `isPrivate()` instead of testing the hash directly.
- **UI:** the create form replaces the optional password toggle with a Public / Private choice (private shows a required password field; a form saved
  before payment restores its choice); the gallery edit modal has the same choice, shows an amber warning plus a confirmation checkbox when switching a
  private gallery to public, and no longer re-sends the unchanged password (it used to rehash and log every visitor out on each save); cards show a
  Private (password) or Public chip; the admin users page edit form has a Visibility selector.
- **Copy:** 15 new strings in all six languages (`newGalleryForm.*`, `galleryCard.*`), covered by a parity test. Draft wording, **needs native review**.

**Tests:** `tests/gallery/visibility.test.ts` (16), `tests/security/gallery-visibility.emu.test.ts` (16, real Firestore emulator and real bcrypt: create,
edit, admin, galleries created before the field existed), i18n parity (3). Also fixed a flaky test from S1-05 (the verify/webhook race test did not
allow the 409 a concurrent webhook delivery now correctly gets since S2-01); three consecutive full emulator runs pass.

**Not done / to check:** (1) the forms were **not exercised in a browser** (they need a signed-in Firebase user); they type-check, build, and the
API rules behind them are tested. (2) Native review of the copy. (3) `firestore.rules` needed no change (galleries are written only through the API).

## S3-06 · contact form and selection submit use the shared limiter (2026-11-26, SEC-2)

`app/api/contact/route.ts` and `app/api/galleries/[id]/selection/submit/route.ts` no longer keep a per-instance `Map` of hits (it reset on every cold start and was not shared between serverless
instances). Both now count in the shared limiter of S3-01: **5 per 10 minutes** per visitor for the contact form, per visitor **and gallery** for selection submit, and a 429 now carries `Retry-After` and
`RateLimit-*` headers. The visitor is identified with `clientIp()` (platform headers first), so forging `X-Forwarded-For` no longer dodges the limit (the contact route used to trust the first entry of that header).
Tests: `tests/security/rate-limited-routes.emu.test.ts` (8): 5 allowed then 429, only allowed messages stored, per-visitor and per-gallery isolation, the forged-header case, and a check that neither route has its own Map.
Until the Upstash credentials are set (D6) the shared limiter is in memory (per instance), as documented in S3-01.

## S3-07 · demo limit and cleanup (2026-11-26, SEC-2)

- **The limit:** `POST /api/demo/create` used to count every demo ever created for an IP, so a visitor was blocked for good after three, and it trusted the first `X-Forwarded-For` entry. It now uses the shared limiter:
  **3 demos per visitor per 24 hours** (counted only for valid requests, so a typo does not use one up) plus a broad cap of 30 attempts per 10 minutes so invalid requests cannot be hammered. Old demo documents no longer count against anyone.
  The 24-hour window starts at the visitor's first demo (a fixed window, not a strictly sliding one). The visitor's IP is **no longer stored** on the demo document. Bad bodies answer 400, not 500.
- **TTL:** each new demo gets `expiresAtTs`, a real Firestore `Timestamp` set to **expiry + 1 day** (the page keeps saying "this demo has expired" for a day instead of a 404). `expiresAt` (a number) is unchanged for the page.
- **Cleanup:** `/api/cron/cleanup` (daily 03:11 UTC, `CRON_SECRET`) deletes demos that expired more than a day ago, in batches of 400 (up to 10,000 per run), idempotent; it leaves documents with no `expiresAt` alone.
  It is the guarantee; the Firestore TTL policy below does the same job but can lag by a day or more and has to be switched on by someone with access to the project.
- **To switch the TTL policy on (one-off, per Firebase project, needs the owner):**
  `gcloud firestore fields ttls update expiresAtTs --collection-group=demo_galleries --enable-ttl --project <PROJECT_ID>`
  (or Firebase console > Firestore > TTL > add a policy for collection group `demo_galleries`, field `expiresAtTs`). Not run from this session.
- Tests: `tests/security/demo-limit-cleanup.emu.test.ts` (9).

## S3-08 · security headers and a report-only CSP (implemented; staging observation outstanding, SEC-3)

`next.config.ts` (read the Next 16 docs on `headers` and CSP first):
- **Every route (API included):** `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera, microphone, geolocation, payment, usb off), `X-Frame-Options: SAMEORIGIN`, and an **enforced**
  `Content-Security-Policy: frame-ancestors 'self'` (that directive is ignored in report-only mode, so framing is restricted by an enforced header). `X-Powered-By` is removed.
- **Pages (not API), production only:** the full policy as **`Content-Security-Policy-Report-Only`** plus `Reporting-Endpoints`. It is built from what the app really loads: GTM / gtag / Meta Pixel (inline snippets, so scripts allow `'unsafe-inline'`; a nonce would force every page to render
  dynamically, which Next's docs say is required), Firebase Auth (Google sign-in popup), Google's image CDN and Drive (gallery photos, the Drive video preview iframe), Vercel Analytics, Stripe (checkout is a redirect). Fonts are self-hosted so no Google font hosts are allowed.
  `object-src 'none'`, `base-uri 'self'`, `form-action 'self' https://checkout.stripe.com`, no `unsafe-eval`, no wildcard script sources.
- **`POST /api/csp-report`:** receives both report formats; 60 per minute per visitor; at most 10 KB; stores nothing; logs one short line per violation with the directive and only the **origin and path** (never the query string) of the blocked resource and the page;
  ignores browser-extension noise.
- **Checked on a production build:** the real response headers on `/`, `/login` and `/api/plans` (pages carry both policies, the API only the basic set); and a Chromium scan of 8 pages in English and Greek (home, login, subscribe, terms, privacy, a landing page, an unknown demo and gallery) found **0 violations**.
  A positive control confirmed the scan works: a disallowed script, image and iframe were detected, reported (not blocked).
- **Not covered by that scan, so the policy is not enforced yet:** the tracking snippets (no tracking ids configured here), signed-in pages, the Google sign-in popup, real gallery photos and videos. These are what the staging/production observation is for.
  Plan: leave it report-only and watch for violations for **3 days** (R2 gate in `04-environments-testing-release.md`) with the real tracking ids and sign-in, then enforce. Violations show up in the Vercel logs as `csp violation` lines (and in Sentry once S0-06 exists).
- **Left alone on purpose:** `Strict-Transport-Security` (Vercel already sends it on production domains; `includeSubDomains` could affect other services on the owner's domain) and `Cross-Origin-Opener-Policy` (it would break Firebase's Google sign-in popup).
- **One behaviour change to know about:** only the app's own pages may now frame its pages (`frame-ancestors 'self'`). If photographers are meant to embed galleries in other sites with an iframe, tell me and the gallery route can allow it.
- Tests: `tests/security-headers.test.ts` (12).

## S3-09 · input validation with zod (2026-11-26, SEC-3, STR-3)

- **`lib/server/http.ts`:** `parseJson(req, schema, { message? })` reads the body and validates it in one step and never throws. A missing, empty, malformed or wrongly shaped body answers the **same 400**: `{ "error": "Invalid request" }` plus, when the JSON parsed but did not fit, `issues: [{ path, message }]` (at most 5, field names only, never the values sent). `badRequest()` builds the same payload.
- **Schemas in `lib/shared/schemas/`:** `public.ts` (verify-password, demo create, contact, selection submit, selection toggle), `galleries.ts` (create / owner PATCH / admin PATCH), `admin.ts` (admin subscription).
- **Routes moved onto the helper:** verify-password, demo/create, contact, galleries POST, galleries/[id] PATCH, admin galleries/[id] PATCH, selection toggle, selection submit, and admin/subscription. The last one called `req.json()` with no guard (bad JSON was a 500) and passed `uid` straight to `.doc()` (a value with a `/` or a non-string threw); it now needs a real document id and one of four known actions.
- **Behaviour deliberately kept:** field-level business rules and their friendly messages (contact: "Please enter your name.", visibility/password rules, honeypot answering `ok`) stay in the routes, because the editor sends every field on each save and the helpers drop junk instead of rejecting the request.
- **Behaviour that changed (stricter, on purpose):** a gallery `name` or `driveUrl` that is not a string (or is absurdly long) is refused with 400; before, `{"name": {...}}` was written to Firestore as an object. The selection toggle needs a non-empty string `item.id`.
- **Left for later (not in this task's list):** `admin/*` routes other than gallery and subscription, `user/language` and `admin/review` (these already parse safely with zod or a try/catch), and Stripe checkout/verify. Listed here so S5-05 can pick them up.
- Tests: `tests/http.test.ts` (10, unit) and `tests/security/input-validation.emu.test.ts` (10: six bad-body shapes against six routes, typed fields, admin ids and actions, contact messages). Whole suite: 196 unit + 265 emulator tests pass; lint stays at 13 warnings.

## S3-04 · photo proxy hardened (2026-11-26, SEC-1)

`/api/photos/proxy` used to fetch **any** Drive file the server's API key could read, for anyone, with a public cache header (and originals could be fetched even in a gallery with downloads turned off or behind a password).

- **Gallery id required.** `?g=<gallery or demo id>&fileId=…&size=thumb|preview|full`. Ids are validated (`[A-Za-z0-9_-]`, ≤ 200), the size must be one of three; anything else is 400. An unknown gallery or an expired demo is 404. The URL is built in one place, `lib/drive/proxy-url.ts`, and every caller passes the gallery id
  (PhotoTile, Lightbox, HeroImage, MasonryGrid zip, CoverPickerModal, GalleryCard).
- **Folder membership.** The file must be in the gallery's folder or one of its subfolders, checked against the same cached folder listing the gallery page uses (`fetchDriveFolder`, refreshed every minute), so it costs no extra Drive call per thumbnail. A foreign file id is **403** and Google is never asked.
  If the listing cannot be read the answer is 502 (fail closed), never an unchecked file.
- **Originals (`size=full`)** additionally need: downloads turned on for the gallery (else 403); for a private gallery, the visitor's unlock cookie for *this* gallery at the *current* password version (else 401; a stale, forged or other-gallery token is refused). The **photographer who owns the gallery and administrators**
  can always fetch originals; they send `Authorization: Bearer`, and the dashboard's "download selection" now does (an `<img>` cannot send a header, so thumbnails stay cookie-free).
- **Rate limits** (shared limiter, per visitor): 900 thumbnails/previews per minute, 1,500 originals per 10 minutes, separate allowances, `429` + `Retry-After`. Generous on purpose: this route is the fallback when Google's CDN fails, and then a whole gallery of thumbnails arrives at once; the limit is meant to stop scripts, not visitors.
- **Caching.** Originals are `private, max-age=3600` (whether they may be served depends on who asks and on the gallery's current settings, so a shared cache must never hold them). Thumbnails/previews of private galleries are `private, max-age=3600`; public galleries keep `public, max-age=86400`.
- **Deliberately not done:** thumbnails and previews of a private gallery are not behind the cookie. The same images are on Google's public CDN under the file id (the Drive folder is public by design, D15), so a cookie here would protect nothing and would break the owner's dashboard covers. Real protection of private photos is S3-02/S3-03.
- Tests: `tests/security/photo-proxy.emu.test.ts` (15): parameters, foreign id denied for every size, subfolder files, another gallery's id, fail-closed, cache headers, `full` denied when downloads are off / without cookie / stale or forged cookie / foreign account, owner and admin allowed, Range, demos (live and expired), rate limits. Whole suite 196 unit + 280 emulator tests; lint stays at 13 warnings.
