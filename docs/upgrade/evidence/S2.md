# S2 evidence

## S2-01 · stripe_events log (2026-11-25)

`stripe_events/{eventId}` is written by the new webhook path (`BILLING_FULFIL_V2=1`) through
`lib/server/repos/stripeEvents.ts` and the dispatcher `lib/server/billing/events/dispatch.ts`.

| State | Meaning | Next delivery of the same event |
|---|---|---|
| `processing` | claimed, handler running | within 5 min: HTTP 409 so Stripe retries; after 5 min: taken over (crashed attempt) |
| `processed` / `ignored` / `needs_review` | finished | skipped, HTTP 200 |
| `failed` | handler error, HTTP 500 sent | claimed again, `attempts` + 1 |

Fields: `type`, `livemode`, `receivedAt`, `lastAttemptAt`, `attempts`, `status`, `processedAt`, `sessionId?`, `uid?`,
`outcome?`, `error?` (max 300 chars, no payloads or stack traces). The claim is a Firestore transaction, so of
simultaneous deliveries exactly one processes. Unmatched payments: `failed` + 500 for 24 h, then `needs_review` + 200
(the Sentry alert and better user resolution are S2-03). Event types with no handler are recorded as `ignored`
until S2-02 adds them. With the flag off nothing is written.

Tests: `tests/billing/stripe-events.emu.test.ts` (12) and the webhook route tests.

**Ops note for R1:** `stripe_events` grows by one small document per delivered event. Add a TTL policy on
`processedAt` later if volume warrants (not needed at current traffic).

## S2-02 · refund, dispute and session-failure handlers (implemented on the D5 default; staging run outstanding)

Behind `BILLING_FULFIL_V2` (new webhook path). Code: `lib/server/billing/events/handlers.ts`, `lib/server/billing/adjust.ts`,
`lib/server/repos/payments.ts`. Tests: `tests/billing/refunds-disputes.emu.test.ts` (16, signed events through the real webhook).

**Policy applied (D5 default; owner confirmed the default on 2026-11-25):**

| Event | Effect |
|---|---|
| `charge.refunded`, full | revoke exactly that payment's `grantedMs` (never below now, lifetime untouched); `payments.status = refunded` |
| `charge.refunded`, partial | **no access change**; `status = partially_refunded`, `needsReview`; event `needs_review`; a later full refund revokes once |
| `charge.dispute.created` | revoke the grant, `status = disputed`, `needsReview`; remembers `revokedMs` |
| `charge.dispute.closed` won / warning_closed | give back `revokedMs` (counted from now), `status = fulfilled` |
| `charge.dispute.closed` lost | grant stays revoked, `status = dispute_lost` (also revokes if "created" was missed) |
| `checkout.session.async_payment_failed` / `.expired` | recorded on the event only, no access or payment change |

Guarantees tested: idempotent (replayed event and a second event for the same refund do nothing); several stacked
payments → only the refunded one is revoked; dispute then refund → revoked once, and a late "won" does not resurrect a
refunded payment; unknown payment → event `needs_review` + 200; payments older than S1-03 (no `paymentIntentId`) are
found through Stripe, revoked by their nominal plan period and flagged for review because their real effect on the
expiry is uncertain (PAY-2).

**Not done yet (blocks "done"):** Stripe CLI triggers (`stripe trigger charge.refunded`, `charge.dispute.created`, …) in
a test-mode deployment, which also needs the production/staging webhook endpoint subscribed to these event types
(R1). The "notify the customer if known" line of the architecture table is not implemented: no customer e-mail on
refund/dispute yet. Admin visibility of `needsReview` payments is S2-09.

## S2-03 · unmatched payments and operator alert (2026-11-25)

- **Policy (unchanged from S2-01, now tested end to end):** user not found and event < 24 h old → HTTP 500 (Stripe retries),
  event `failed`; after 24 h → HTTP 200, event `needs_review`, one operator alert.
- **Better user resolution** (`fulfil.ts`): `metadata.uid` → `client_reference_id` → the user whose document already has this
  Stripe **customer id** (new) → customer e-mail. A customer id shared by several users is never guessed.
  (Stripe customer *metadata* is not read: we do not set it today; S4 creates customers and stores their id on the user,
  which this lookup then uses.)
- **Operator alert (D17):** `lib/server/notify/admin.ts` e-mails `ADMIN_ALERT_EMAIL` (no address → log only). It is sent once,
  when an event first reaches `needs_review`, for **any** such event: unmatched payment, partial refund, refund with no matching
  payment, legacy payment revoked, unexpected dispute status. `stripe_events.alertedAt` records that it went out; duplicate
  deliveries are skipped before any handler runs, so they cannot alert again. Content: event type/id/mode, outcome, session id,
  user id, a Stripe dashboard link; no customer e-mail address, no card data. A mail failure (false or exception) never changes
  the webhook response.
- Tests: `tests/billing/unmatched-alert.emu.test.ts` (15).

**Split from the original task text:** the Sentry alert and the daily digest are S2-16 (need S0-06); customer e-mails and in-app
notices are S2-14 / S2-15 (need S2-13, language on the user document). Plan updated: D17, G16, S2-13 … S2-16.

## S2-04 · reconciliation cron (implemented and tested on the emulator; staging proof outstanding)

`/api/cron/reconcile-payments` (`app/api/cron/reconcile-payments/route.ts`, logic in `lib/server/billing/reconcile.ts`),
scheduled hourly at :17 in `vercel.json`.

- **Auth:** `Authorization: Bearer $CRON_SECRET` (timing-safe compare). No `CRON_SECRET` configured → 500, the job refuses
  to run; wrong or missing secret → 401.
- **Flag:** does nothing (`skipped`) until `BILLING_FULFIL_V2` is on, so it never runs beside the old fulfilment path.
- **Job:** lists Checkout Sessions from the last 48 h (paginated); for each *complete, settled* session created by this app
  (has a uid marker; other products on the same Stripe account are ignored) without a `payments` document it calls
  `fulfilCheckoutSession(…, { source: "reconcile" })`. Idempotent, so a late webhook racing the job cannot double-grant.
  One bad session never stops the rest. Summary returned and logged: `checked, alreadyFulfilled, healed, unmatched, errors,
  pending, skippedForeign, streak, alerted`.
- **Alert (D17, e-mail):** one heal is tolerated; when the job heals (or fails to) on **2 consecutive runs** it e-mails
  `ADMIN_ALERT_EMAIL` once per streak ("the webhook is probably failing"); a clean run resets. State in
  `system_state/reconcile-payments`. If the mail fails the alert is retried on the next bad run.
- Tests: `tests/billing/reconcile.emu.test.ts` (14).

**Why it is not marked done:** the task's "done when" is *dropping a webhook in staging is healed within one run*. The emulator
test reproduces it (paid session with no payment document → healed, second run clean), but the staging run needs the test
deployment, `CRON_SECRET` and Stripe test keys.

**Ops notes for R1:** (1) set `CRON_SECRET` in Vercel (production). (2) Vercel Cron only runs on the **production**
deployment, and **Hobby plans allow cron jobs once per day only**: hourly needs Pro; on Hobby change the schedule in
`vercel.json` to daily (the 48 h window still covers it). (3) `ADMIN_ALERT_EMAIL` plus the SMTP settings must be set for the
alert to go out.

## S2-06 · back-fill reports (2026-11-25, PAY-7)

Read-only scripts: `scripts/backfill/report.ts`, logic in `lib/server/billing/backfill.ts`. They only ever call `.get()` / `.getAll()` and
Stripe `list`; tests snapshot the data before and after and assert nothing changed. CSVs go to `scripts/backfill/out/`
(git-ignored: they contain customer e-mail addresses). Spreadsheet formula injection is defused (a cell starting with `= + - @` is
written as text).

```bash
npx tsx --env-file=.env.local scripts/backfill/report.ts                # both reports
npx tsx --env-file=.env.local scripts/backfill/report.ts --report a     # one report
```

**Report A: replay.** For each user with payments, replay the payments oldest-first with the new stacking rule
(`computeExpiry` at each payment's `activatedAt`) and compare with `users.subscriptionExpiresAt`. Differences of a day or less are
ignored. Payments whose grant was taken back (`refunded`, `disputed`, `dispute_lost`) are not counted. Skipped: comped/lifetime accounts
(`compGranted` or a lifetime expiry), the admin, and payments of deleted users (counted in the summary). Columns: `uid, email,
paymentsReplayed, expectedExpiry, currentExpiry, deltaDays, plan, category, bothExpired, note` (the documented seven plus
`category`, `bothExpired`, `note`).
- `under_extended`: payments add up to more time than the account has (for example PAY-2). These are the candidates for correction.
- `over_extended`: the account has more time than its payments explain (an admin extension, say). **Review only; the apply script
  (S2-08) never reduces anyone's access.**
- Ordered most urgent first: customers who should have access today but do not, then others affected today, then accounts where both
  dates have already passed (no effect on access), biggest gap first.

**Report B: missing payments.** Complete, settled Checkout Sessions from the last 13 months that were created by this app (they carry a
uid marker; other products on the same Stripe account are ignored) and have no `payments/{sessionId}` document. Columns: `sessionId,
created, uid, email, amount, currency, paymentIntent, planId, interval, livemode, note`. Against production it needs the live Stripe
key and `APP_ENV=production` (live keys are refused anywhere else on purpose).

**Verified:** 21 tests (`tests/billing/backfill.test.ts`, `backfill.emu.test.ts`) and one run of the real CLI against the emulator
with seeded data (the seeded PAY-2 customer was flagged 30 days under-extended; the CSV was correct; no repo files were left behind).
**Not yet run against real data:** that is S2-07 (owner review gate) and needs read-only production credentials.

**Known limits to remember when reading the output:** accounts that had time added by the old code's quirks other than PAY-2 will show
up as over- or under-extended; payments made before S1-03 have no recorded grant, so the nominal plan period is used; Report A cannot
see sessions that never reached the `payments` collection (that is what Report B is for, and a customer in Report B may also be
missing from Report A).

## S2-08 · back-fill apply script (implemented and rehearsed on the emulator; staging rehearsal and production run outstanding)

`scripts/backfill/apply.ts`, logic in `lib/server/billing/backfill-apply.ts`. It corrects account expiries for customers the owner approved after reading
Report A (S2-06/S2-07). Report B (paid sessions with no payment record) is **not** applied by this script: sessions from the last 48 hours are healed by
the reconciliation job (S2-04); older ones need their own decision after the owner has seen the report.

```bash
# 1. dry run (default): shows exactly what would change, writes nothing
npx tsx --env-file=.env.local scripts/backfill/apply.ts --approved scripts/backfill/out/approved.csv
# 2. apply: needs who approved and the project id repeated back
npx tsx --env-file=.env.local scripts/backfill/apply.ts --apply --approved scripts/backfill/out/approved.csv \
    --approved-by "Owner Name" --confirm-project <FIREBASE_ADMIN_PROJECT_ID>
```

**The approved file** is a copy of Report A with an extra `approved` column. A row is approved only if that cell says `yes` (also `y`, `true`, `1`, `x`);
anything else, or an empty cell, is not. A file without the `uid`, `expectedExpiry` and `approved` columns is refused.

**Safety properties (all tested):**
- Refuses to run without `--approved <file>` (dry run too); applying also needs `--approved-by` and `--confirm-project` matching `FIREBASE_ADMIN_PROJECT_ID`.
- Only rows marked yes and categorised `under_extended` are considered. **Access is only ever raised**: `over_extended` rows are skipped even if marked yes, and a
  row whose recomputed expiry would be lower than the account's current one is skipped.
- Every row is **re-checked against today's data**: skipped if the account's expiry or its payments changed since the report (the file is a proposal, not an
  instruction), if the user no longer exists, or if the account is now comped or lifetime.
- The expiry change and its `audit_log` record (`actorUid: script:backfill-s2-08`, before/after, `approvedBy`, run id, source file) are written in **one
  transaction**; the record has a deterministic id, so the same correction can never be applied twice, even by simultaneous runs.
- **Idempotent:** a second run changes nothing; a report regenerated afterwards no longer lists the fixed accounts.
- A result CSV (`apply-<run>.csv` / `dry-run-<run>.csv` in the git-ignored `scripts/backfill/out/`) records the outcome of every row.

**Rehearsal (emulator):** report -> owner approves one of two PAY-2 customers -> guard rails refuse three bad invocations -> dry run (nothing written) -> apply (only the
approved customer changed) -> apply again (nothing) -> report again (the unapproved customer is still listed). 18 tests in
`tests/billing/backfill-apply.emu.test.ts`.

**Outstanding for "done":** rehearsal on staging (deferred, D12). **Production:** only after S2-07 (the owner has reviewed the report and produced
`approved.csv`), a dry run against production shown to the owner, then the `--apply` run.

## S2-13 · the user's language is stored on their account (2026-11-26)

So the server can write to a customer in their own language (payment e-mails S2-14, renewal reminders S9-03).

- **`lib/i18n/languages.ts`** (pure, importable from server code): the one list of the six languages, `isLang`, and `decideLanguageSync`, the rule for when to sync.
  `lib/i18n/index.tsx` now takes its `Lang` type from it.
- **`PUT /api/user/language`:** signed-in users only; body validated against the six languages (`zod` enum, anything else is 400); 20 requests a minute per user; uses
  `update()`, so it never creates a half-empty profile for an account with no user document (409 instead); touches only `language` and `languageUpdatedAt`.
- **`components/auth/LanguageSync.tsx`** (renders nothing, inside the auth provider): once the signed-in user's profile is loaded it applies `decideLanguageSync`:
  a language chosen on this device is stored if the account does not have it; with no choice on this device the account's language is **adopted** (it follows the user to
  a new device); a brand-new account gets the current (detected or default) language stored once. One attempt per value, failures ignored: the UI never depends on it.
- **`userLanguage(user)`** (`lib/server/user-language.ts`): what to write to a user in; English when nothing valid is stored. Use this in S2-14 and S9-03.
- **`firestore.rules`:** `language` and `languageUpdatedAt` are added to the server-only `locked()` fields, so a browser cannot write them directly (it could otherwise store junk that the
  e-mail code would have to defend against).

**Tests:** `tests/language.test.ts` (8: list matches the translations, `isLang`, `userLanguage`, every case of the sync rule, and a check that acting on a decision always settles, so
it cannot loop); `tests/security/user-language.emu.test.ts` (10: the endpoint, plus **Firestore rules tests** with `@firebase/rules-unit-testing`, a new dev dependency: the browser cannot
write `language`, can still update its name, and the existing protections for subscription fields and other users' profiles hold).

**Not checked in a browser:** the `LanguageSync` component itself (needs a signed-in user); its decision logic and the endpoint are tested. Existing accounts get their language stored the next
time they sign in and have a profile loaded.

## S2-14 · customer e-mails for payment events (implemented; native copy review outstanding)

Customers are now told, by e-mail and in their own language, what happened to their access. Part of D17; behind `BILLING_FULFIL_V2` like the handlers that trigger it.

| Event | Message | Access sentence |
|---|---|---|
| full refund (changed something) | "Your refund has been processed" | "runs until <date>" / "has ended" / "unchanged" for lifetime |
| partial refund | "A partial refund has been processed" (amount and refunded part) | "runs until <date>" / "unchanged" |

| dispute won | "Your access has been restored" | "runs until <date>" |
| dispute lost | "An update on your payment dispute" | time removed; "runs until <date>" / "has ended"; link to subscribe again |

An expired (abandoned) Checkout Session sends nothing. A repeat event that changed nothing sends nothing.

**Code:** `lib/server/notify/templates.ts` (pure: six kinds x six languages, one placeholder system, plain-text and HTML, the customer's name HTML-escaped, no card data, session ids or other users' data),

  cover the same payment, and even when called concurrently. A message that failed is tried again if the event is retried. No message content is stored.
- **Best effort:** it never throws and cannot change the webhook response; a mail failure (false or exception), a user without an e-mail address, or a user who no longer exists are logged and skipped.
- **Reply-To** is the support address (`getSupportEmail()`).

**Tests:** `tests/notify-templates.test.ts` (46: every kind in every language is complete and filled in, the access wording, lifetime, escaping, no ids), `tests/billing/customer-notices.emu.test.ts` (20: real webhook events in, e-mails out:
