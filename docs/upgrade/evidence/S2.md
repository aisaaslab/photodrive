# S2 evidence

## S2-01 · stripe_events log (2026-11-25)

`stripe_events/{eventId}` is written by the new webhook path (`BILLING_FULFIL_V2=1`) through
`lib/server/repos/stripeEvents.ts` and the dispatcher `lib/server/billing/events/dispatch.ts`.

| State | Meaning | Next delivery of the same event |
|---|---|---|
| `processing` | claimed, handler running | within 5 min: HTTP 409 so Stripe retries; after 5 min: taken over (crashed attempt) |
| `processed` / `ignored` / `needs_review` | finished | skipped, HTTP 200 |
| `failed` | handler error, HTTP 500 sent | claimed again, `attempts` + 1 |

Fields: `type`, `livemode`, `receivedAt`, `lastAttemptAt`, `attempts`, `status`, `processedAt`, `sessionId?`, `uid?`,
`outcome?`, `error?` (max 300 chars, no payloads or stack traces). The claim is a Firestore transaction, so of
simultaneous deliveries exactly one processes. Unmatched payments: `failed` + 500 for 24 h, then `needs_review` + 200
(the Sentry alert and better user resolution are S2-03). Event types with no handler are recorded as `ignored`
until S2-02 adds them. With the flag off nothing is written.

Tests: `tests/billing/stripe-events.emu.test.ts` (12) and the webhook route tests.

**Ops note for R1:** `stripe_events` grows by one small document per delivered event. Add a TTL policy on
`processedAt` later if volume warrants (not needed at current traffic).

## S2-02 · refund, dispute and session-failure handlers (implemented on the D5 default; staging run outstanding)

Behind `BILLING_FULFIL_V2` (new webhook path). Code: `lib/server/billing/events/handlers.ts`, `lib/server/billing/adjust.ts`,
`lib/server/repos/payments.ts`. Tests: `tests/billing/refunds-disputes.emu.test.ts` (16, signed events through the real webhook).

**Policy applied (D5 default; owner confirmed the default on 2026-11-25):**

| Event | Effect |
|---|---|
| `charge.refunded`, full | revoke exactly that payment's `grantedMs` (never below now, lifetime untouched); `payments.status = refunded` |
| `charge.refunded`, partial | **no access change**; `status = partially_refunded`, `needsReview`; event `needs_review`; a later full refund revokes once |
| `charge.dispute.created` | revoke the grant, `status = disputed`, `needsReview`; remembers `revokedMs` |
| `charge.dispute.closed` won / warning_closed | give back `revokedMs` (counted from now), `status = fulfilled` |
| `charge.dispute.closed` lost | grant stays revoked, `status = dispute_lost` (also revokes if "created" was missed) |
| `checkout.session.async_payment_failed` / `.expired` | recorded on the event only, no access or payment change |

Guarantees tested: idempotent (replayed event and a second event for the same refund do nothing); several stacked
payments → only the refunded one is revoked; dispute then refund → revoked once, and a late "won" does not resurrect a
refunded payment; unknown payment → event `needs_review` + 200; payments older than S1-03 (no `paymentIntentId`) are
found through Stripe, revoked by their nominal plan period and flagged for review because their real effect on the
expiry is uncertain (PAY-2).

**Not done yet (blocks "done"):** Stripe CLI triggers (`stripe trigger charge.refunded`, `charge.dispute.created`, …) in
a test-mode deployment, which also needs the production/staging webhook endpoint subscribed to these event types
(R1). The "notify the customer if known" line of the architecture table is not implemented: no customer e-mail on
refund/dispute yet. Admin visibility of `needsReview` payments is S2-09.

## S2-03 · unmatched payments and operator alert (2026-11-25)

- **Policy (unchanged from S2-01, now tested end to end):** user not found and event < 24 h old → HTTP 500 (Stripe retries),
  event `failed`; after 24 h → HTTP 200, event `needs_review`, one operator alert.
- **Better user resolution** (`fulfil.ts`): `metadata.uid` → `client_reference_id` → the user whose document already has this
  Stripe **customer id** (new) → customer e-mail. A customer id shared by several users is never guessed.
  (Stripe customer *metadata* is not read: we do not set it today; S4 creates customers and stores their id on the user,
  which this lookup then uses.)
- **Operator alert (D17):** `lib/server/notify/admin.ts` e-mails `ADMIN_ALERT_EMAIL` (no address → log only). It is sent once,
  when an event first reaches `needs_review`, for **any** such event: unmatched payment, partial refund, refund with no matching
  payment, legacy payment revoked, unexpected dispute status. `stripe_events.alertedAt` records that it went out; duplicate
  deliveries are skipped before any handler runs, so they cannot alert again. Content: event type/id/mode, outcome, session id,
  user id, a Stripe dashboard link; no customer e-mail address, no card data. A mail failure (false or exception) never changes
  the webhook response.
- Tests: `tests/billing/unmatched-alert.emu.test.ts` (15).

**Split from the original task text:** the Sentry alert and the daily digest are S2-16 (need S0-06); customer e-mails and in-app
notices are S2-14 / S2-15 (need S2-13, language on the user document). Plan updated: D17, G16, S2-13 … S2-16.

## S2-04 · reconciliation cron (implemented and tested on the emulator; staging proof outstanding)

`/api/cron/reconcile-payments` (`app/api/cron/reconcile-payments/route.ts`, logic in `lib/server/billing/reconcile.ts`),
scheduled hourly at :17 in `vercel.json`.

- **Auth:** `Authorization: Bearer $CRON_SECRET` (timing-safe compare). No `CRON_SECRET` configured → 500, the job refuses
  to run; wrong or missing secret → 401.
- **Flag:** does nothing (`skipped`) until `BILLING_FULFIL_V2` is on, so it never runs beside the old fulfilment path.
- **Job:** lists Checkout Sessions from the last 48 h (paginated); for each *complete, settled* session created by this app
  (has a uid marker; other products on the same Stripe account are ignored) without a `payments` document it calls
  `fulfilCheckoutSession(…, { source: "reconcile" })`. Idempotent, so a late webhook racing the job cannot double-grant.
  One bad session never stops the rest. Summary returned and logged: `checked, alreadyFulfilled, healed, unmatched, errors,
  pending, skippedForeign, streak, alerted`.
- **Alert (D17, e-mail):** one heal is tolerated; when the job heals (or fails to) on **2 consecutive runs** it e-mails
  `ADMIN_ALERT_EMAIL` once per streak ("the webhook is probably failing"); a clean run resets. State in
  `system_state/reconcile-payments`. If the mail fails the alert is retried on the next bad run.
- Tests: `tests/billing/reconcile.emu.test.ts` (14).

**Why it is not marked done:** the task's "done when" is *dropping a webhook in staging is healed within one run*. The emulator
test reproduces it (paid session with no payment document → healed, second run clean), but the staging run needs the test
deployment, `CRON_SECRET` and Stripe test keys.

**Ops notes for R1:** (1) set `CRON_SECRET` in Vercel (production). (2) Vercel Cron only runs on the **production**
deployment, and **Hobby plans allow cron jobs once per day only**: hourly needs Pro; on Hobby change the schedule in
`vercel.json` to daily (the 48 h window still covers it). (3) `ADMIN_ALERT_EMAIL` plus the SMTP settings must be set for the
alert to go out.

## SMTP for all e-mail (D17, owner choice 2026-11-25)

`sendEmail` already supports SMTP (`CONTACT_SMTP_*`, used when `RESEND_API_KEY` is unset). Changes: connection (10 s),
greeting (10 s) and socket (15 s) timeouts so a slow mail server cannot stall a Stripe webhook that is sending an operator
alert (nodemailer's default is about two minutes). `tests/email.test.ts` (5, nodemailer mocked) pins the configuration:
STARTTLS on 587, port/secure/from honoured, Resend never contacted when its key is unset, failure returns `false` and never
logs the password. **Not verified against a real SMTP server** (no credentials in this session): send a test alert once the
variables are set.
