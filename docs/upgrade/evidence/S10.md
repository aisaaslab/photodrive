## S10-03 Drive folder check (2026-11-27)

- `lib/drive/check.ts`: asks Drive (read-only key) whether a folder is reachable and what is in it: `ok` (photo/video counts, lower bounds when over one page, "photos are in sub-folders" probing up to 5 sub-folders), `empty`, `unsupported` (only documents), `notFound` (not shared and missing are indistinguishable to the key), `notFolder` (a single-file link), `unavailable` (quota, key, outage, network: never reported as "not found").
- `POST /api/drive/check`: signed-in users only, rate limited (30/min per user and IP), always 200 with a `status` except malformed body (400) and rate limit (429); no Drive key configured means `unavailable`.
- Create form: after typing pauses (600 ms) and the link looks right, a live message under the field in six languages. It only informs: creating the gallery is never blocked by it, so a Drive outage cannot stop a photographer.
- Proof: `tests/drive-check.test.ts` (10, fake Drive), `tests/drive-check-route.test.ts` (6: auth, rate limit, bad body, no key, answer, all messages in six languages); browser snapshot step `34b` records "Folder found: 3 photos and videos." for the stand-in's shared folder. `fake-drive.cjs` now answers the folder-metadata request.
- Edit form: the owner dialog's Drive field is read-only by design (to change the folder, create a new gallery), so the check applies to the create form only.

## S9-06 Switch off downloads once a selection is sent (2026-11-27)

- New per-gallery option `disableDownloadAfterSubmit` (settings dialog, Privacy & downloads; shown only while downloads are on; six languages). When a client sends their selection while it is on, the submit route stamps `downloadsLockedAt` on the gallery.
- One rule, `lib/gallery/downloads.ts` (`downloadsAllowed`), used by the photo proxy and media route (through `loadProxyGallery`), download-all and the gallery page. The owner and administrators are never affected. The client's buttons hide at once after sending (the submit response says `downloadsLocked`), and the server refuses anyway.
- Changing the option clears the stamp (off gives downloads back; on later does not lock retroactively). Saving with the option unchanged does not clear it: the dialog sends every field on each save, and an early version of the route would have re-opened downloads on any save (caught while writing the test).
- Proof: `tests/gallery-downloads.test.ts` (5) and `tests/security/download-lock.emu.test.ts` (6, emulator): before sending, downloads work; after sending, proxy, signed media route and download-all each answer 403 while the owner still gets 200; no option means no change; re-saving does not unlock; toggling resets; non-owner cannot change it.
- Browser: gallery snapshot identical to its baseline; dashboard snapshot differs only by the new checkbox and the extra request field (baseline re-taken on purpose).

## S10-02 Gallery stats (2026-11-27)

- `gallery_stats/{galleryId}` (server-only; the catch-all Firestore rule denies browsers, now asserted in `tests/rules`): running totals of views, downloads and favourites, a bucket per UTC day, and the time of the last view. Increments only (no read) on the hot paths, so a 300-photo download is 300 cheap writes, not 300 transactions. Buckets older than 30 days are dropped when a view is recorded. Counting is best-effort and never breaks the request it counts.
- **Views** (`POST /api/galleries/[id]/view`, called once by `ViewBeacon` on the gallery page): once per browser session through a session cookie that only says "counted"; reloads and extra tabs count nothing; private galleries count only for a visitor who unlocked them; demo, switched-off and unknown galleries count nothing; rate limited.
- **Downloads**: an original delivered to a visitor by the photo proxy or the signed media route; a "Download all" zip counts its photos; the owner's and administrators' fetches and refused requests are not counted. **Favourites**: a photo newly added by a visitor.
- Dashboard card: views, downloads, favourites and the last visit (or "No visits yet"), six languages, accessible labels; `GET /api/galleries` attaches the counts with one more batched read. Deleting a gallery deletes its counts.
- Privacy: counts and one timestamp only; no IP, browser details or visitor id. Documented in `docs/security-model.md` ("Usage counts"), including that the photographer's own visits to the public page are counted.
- Proof: `tests/gallery-stats.test.ts` (6) and `tests/security/gallery-stats.emu.test.ts` (11, emulator, real routes: scripted visit pattern, reload does not inflate, private/demo/off, owner downloads excluded, refused downloads not counted, zip, favourites add/remove, list, delete, 30-day pruning). Whole emulator suite: 41 files, 449 tests pass. Gallery snapshot identical to baseline; dashboard snapshot differs only by the stats line on each card (baseline re-taken on purpose; its Favorites selector now targets the button by role because the stats line carries screen-reader labels).
