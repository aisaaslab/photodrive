## S9-05 Gallery expiry date and S9-04 Gallery availability after plan lapse (2026-11-27)

**One rule** (`lib/gallery/availability.ts`, pure, 15 unit tests): a gallery is unavailable when an administrator switched it off, when its own `expiresAt` has passed, or when its owner's plan ended more than 14 days ago (only while `GALLERY_LAPSE_ENFORCE=1`). In the 14 days after a plan ends the gallery stays online ("grace") and the owner is told. Lifetime owners, administrators and accounts with no recorded expiry are never lapsed. `lib/server/gallery-availability.ts` adds the owner lookup: an active plan is cached 30 s per server instance, a plan in grace or lapsed is never cached, so **a renewal restores galleries on the very next request on every server**.

**Used everywhere a visitor can reach a gallery:** the gallery page (and its no-index metadata), photo proxy, signed media route, view count, favourites (read and write), selection submit, download-all and the password check all answer "not found" / show the unavailable page. The owner and administrators keep access to an expired or lapsed gallery (cover, selection, zip), so they can extend or renew; a gallery switched off by an administrator still blocks everyone, as before. Nothing is deleted.

**Rollout safety:** `GALLERY_LAPSE_ENFORCE` is off by default (documented in `.env.example`), so the live shop does not change until the owner turns it on; the owner is not even read while it is off. A gallery's own optional expiry date is the photographer's own choice and works regardless.

**Photographer-facing:**
- Optional "Gallery expires on" date in the create form and in the settings dialog (six languages). Sent as a plain date, stored as the end of that UTC day, refused if it is not a real date. Changing or clearing it restores the gallery at once.
- Dashboard card: "Expires <date>", "Offline since <date>", "Online until <date> (plan ended)" or "Offline: your plan ended".
- Dashboard banner: after the plan ends it says the galleries stay online until a date (grace) or that they are offline and nothing was deleted (lapsed), with the Renew button. It is worded from `lapse.enforced` in `GET /api/user/subscription`, so it never promises something the server is not doing.

**Proof**

Covers every visitor route for an expired gallery; before the date; owner still allowed; extending and clearing; bad dates refused; only the owner can set it; set on create; enforcement off = no change at all; grace (online, with the end date); after grace (all refused, owner allowed, nothing deleted); renewal restores at once; owners with no expiry / lifetime / administrator are never offline; the subscription endpoint's `lapse` info; an offline private gallery cannot be unlocked.

## S9-03 Renewal reminder e-mails (2026-11-27)

**What customers get** (each at most once per plan period, in their stored language, English if none; wording is a DRAFT in six languages and needs native review):
- `expiring14`: the plan ends in 14 days or less; `expiring3`: in 3 days or less; `lapsed`: it ended in the last 3 days. Only the most urgent applicable message is due, so a missed run never sends two at once, and a plan that lapsed long ago is never mailed (so switching the job on does not blast history).
- Excluded: lifetime accounts, accounts an administrator granted by hand (`compGranted`), accounts with no recorded expiry, accounts with no e-mail address.
- The wording follows what the server really does: while `GALLERY_LAPSE_ENFORCE` is off the e-mails never mention galleries going offline, only that nothing is deleted. They contain the customer's first name, their plan's end date, a renew link and the support address; nothing else.

**How it works** (`lib/shared/reminders.ts` pure rules, `lib/server/reminders.ts` the job, `app/api/cron/reminders/route.ts`, daily 09:37 UTC in `vercel.json`):
- Idempotent: before sending, the job claims the reminder in a transaction that re-checks it against the current document, recording `users.remindersSent["<kind>:<expiry day>"]`. Two runs at once send once; a renewal (new expiry day) starts afresh; a failed send gives the claim back so the next run retries.
- Limits: at most 200 e-mails per run (the rest are still due the next day, the windows are days wide); `CRON_SECRET` required like the other cron routes.
- **Switched off by default** (`REMINDERS_MODE=off`). Modes: `off`, `dry-run` (works out who would get what, reports uid / kind / language / **masked** address, sends and records nothing) and `send`. `?mode=dry-run` on the URL can lower any mode to a dry run; nothing on the URL can turn sending on.
- The 14- and 3-day reminders are held back until `BILLING_FULFIL_V2=1`: until then the subscribe page sends a still-active customer back to the dashboard, so their "renew" link would lead nowhere. The "plan has ended" notice does not depend on it.

**How the owner reviews before anything is sent**
1. Set `REMINDERS_MODE=dry-run` (and `CRON_SECRET`) in Vercel, deploy.
2. Run it by hand, or wait for the daily run: `curl -H "Authorization: Bearer $CRON_SECRET" https://<your domain>/api/cron/reminders`. The response (and the Vercel log) lists every planned reminder: uid, kind, language, masked address and expiry day.
3. When the list looks right (and the wording has had native review), set `REMINDERS_MODE=send`.
