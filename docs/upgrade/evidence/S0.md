## S0-06 Error monitoring with Sentry (2026-11-27)

**State: built and proved against a local stand-in; waiting for the owner's Sentry project.** The task's own "done when" (a staging-only test error shows up *in Sentry* with release and environment) needs a Sentry account and DSN (decision D12, deferred by the owner), so the checkbox stays `[~]` until the owner has run the test below once. Everything that can be proved without the account is proved.

**What was added** (`@sentry/nextjs` 11.20.0, pinned; Next 16 is supported by it):
- **Inert until configured.** No DSN → nothing is initialised, `next.config.ts` is not even wrapped, no request leaves the app (`lib/shared/monitoring.ts` decides; unit-tested).
- **Three setups:** `instrumentation.ts` (`register()` loads the Node or edge setup; `onRequestError = Sentry.captureRequestError` reports every error Next.js catches in a route, page or server component), `sentry.server.config.ts`, `sentry.edge.config.ts`, and `instrumentation-client.ts` for the browser (plus `onRouterTransitionStart`). `app/error.tsx` and a new `app/global-error.tsx` report render crashes (global-error covers a failure in the root layout itself).
- **API error paths.** `lib/server/monitor.ts` (`captureServerError`, never throws, no-op without a client) is called by the structured logger whenever `logger.error` is given an error object. Because every `route()` wrapper, the Stripe routes, the cron jobs and the webhooks already log their failures through that logger, they all reach Sentry with a `scope` and `request_id` tag; expected outcomes (400, 401, 404...) are not reported.
- **Release and environment.** Release = the commit (`VERCEL_GIT_COMMIT_SHA`, or `SENTRY_RELEASE`); environment = `SENTRY_ENVIRONMENT`, else `APP_ENV`, else `NODE_ENV`, so staging and production never mix.
- **Privacy** (`scrubEvent`, run on every event in `beforeSend`; `sendDefaultPii: false`): no user, IP, server name, cookies, request body, query string, `authorization` / `cookie` / `stripe-signature` / forwarded-IP headers, no `extra`; secret-looking URL parameters (`token`, `sig`, `session_id`, `password`...) are replaced; e-mail addresses in messages, exceptions and breadcrumbs become `[email]`. No session replay.
- **Source maps** when `SENTRY_ORG`, `SENTRY_PROJECT` and `SENTRY_AUTH_TOKEN` are set at build time: uploaded, then deleted from the output (never public); without the token the build is unchanged.
- **Staging test route** `GET /api/admin/sentry-test`: administrators only, answers 404 unless `SENTRY_TEST_ROUTE=1`, and 404 in production even then; raises a deliberate error. CSP `connect-src` also allows the EU and US ingest hosts.
- `.env.example` documents every variable.

**Proof**
- Unit: `tests/monitoring.test.ts` (6: DSN / environment / release / sample-rate rules and the whole privacy filter), `tests/monitor-capture.test.ts` (4: no-op when off, tags when on, never throws, only `logger.error` with an error object reports).
- Emulator: `tests/security/sentry-test-route.emu.test.ts` (4: 404 without the flag, 404 in production, deliberate 500 and report when enabled, 403 for a customer); the admin permission matrix still passes with the new route.
- **End to end with a stand-in ingest server** (`scripts/verify/browser/sentry-local.cjs`; production build made with a DSN pointing at `127.0.0.1:18999`, `SENTRY_ENVIRONMENT=staging`, `VERCEL_GIT_COMMIT_SHA=abc1234567890`): the test route answered 500 with no message shown; the event reached the stand-in with `release = abc1234567890`, `environment = staging`, tag `scope = admin.sentry-test`, and **no** cookie, authorization header, user or e-mail; an error thrown in a browser page also arrived with release and environment, its e-mail address masked, a `?token=` in the page URL removed, and no user (10 checks).
- The build without any Sentry variable is unchanged (the default runs of every browser script above).
