# Evidence: Sprint 8 (admin back office II)

## S8-01 Payments screen `/dashboard/admin/payments` (2026-11-27)

**What an operator gets** (new "Payments" tab in the back office):
- **Totals per currency** for the last 30 days (net, number of payments, amount refunded), each currency on its own and never added together (PAY-6); free-code checkouts carry no money and are left out; a very busy month is cut at 3,000 payments and says so.
- **Needs attention** queue, oldest first: Stripe events still waiting for a person (a payment Stripe took that could not be matched to a customer, a partial refund, a refund or dispute for a payment with no record, ...) and payments flagged for review (open dispute, ...), each with the customer, age, the Stripe error and a link into the Stripe dashboard (test or live path).
- **Every payment**, newest first, paged with a cursor, with a status (Paid, Free code, Refunded, Partially refunded, Disputed, Dispute lost, Needs review), filter chips (Everything, Paid, Free codes, Refunded, Disputed, Needs review) and search by customer e-mail (or its start), Checkout Session id (`cs_…`, or its start) or payment id (`pi_…`).
- **A payment drawer**: amount, status, how it was paid, plan and days granted, access end, who fulfilled it, invoice, the customer (link to Users), the Stripe events that touched it, what administrators did, and the actions.

**Resolving an item without leaving the page** (the task's done-when):
- *Paid, but no customer matched* → "Credit a customer…": search the customer by e-mail, confirm, and the payment is credited through the same idempotent path as the webhook (`fulfilCheckoutSession`, now with an optional administrator-chosen customer); the waiting Stripe event closes itself.
- *Partial refund, dispute, refund for an unknown payment, ...* → "Mark reviewed…" with a note (the existing review endpoint, which now writes an audit entry).
- *Any payment* → "Re-sync with Stripe" (asks first; safe to repeat: access is never granted twice, an already-fulfilled payment reports "nothing changed"). A session Stripe has not collected grants nothing and says so; an unknown session, an unconfigured or unreachable Stripe each give a clear message and change nothing.
- **Every action is audited** under the administrator (`payment.resync`, `payment.review`, `payment.review_event`), with the note and the before/after state.
- A re-sync closes only the "unmatched payment" event of that session. It never closes a partial-refund or dispute event, which needs a person's decision (this bug was found by the browser walkthrough, then fixed and covered by a test).

**API** (all administrator-only): `GET /api/admin/payments` (list, filter, search, cursor), `/summary`, `/attention`, `/[id]` (detail) and `POST /[id]/resync`. No new database index is needed (the list is ordered by `activatedAt`, filters apply to the page in memory, the other queries reuse existing indexes).

**Test hook added:** `STRIPE_API_BASE_URL` points the Stripe client at a local stand-in (used by the browser check). It is **ignored when `APP_ENV=production`**, so a stray value can never redirect real payment calls (tested).

**Proof**

- `tests/billing/admin-payments.emu.test.ts` (19, emulator, real routes, fake Stripe): customers get 403 and visitors 401 on every endpoint; newest first with e-mail and Stripe link; each filter, old payments without a status counting as paid; cursor paging shows every payment once; a filter pages past non-matching payments; search by session id / payment id / e-mail prefix; totals; the attention queue; the detail view with its events and history; re-sync: credits a missed payment once and audits it, the second run changes nothing, an unmatched payment asks for the customer and naming one credits them and closes the waiting event, asking to credit someone else when it was already credited changes nothing, a session Stripe has not collected grants nothing, and the error cases; a re-sync never closes a partial-refund event; marking reviewed leaves an audit entry with the note.

## S8-02 Support inbox `/dashboard/admin/support` (2026-11-27)

**What an operator gets** (new "Support" tab; the older inbox in Settings keeps working until S8-05 retires it):
- The contact-form messages as an inbox: **Open** (everything not resolved, the default), **Unread**, **Resolved**, **Everything**, each chip with its count, newest first, paged. Unread messages are bold with a dot.
- **Search** across the sender, e-mail, subject, message text and the internal note (every word must match, any case).
- Each message is **matched to the customer account** with the sender's e-mail address (looked up through Firebase Auth, so it works for every account, including ones that lack the Users search index). A "Customer" badge shows in the list; the drawer shows name, plan state ("active until…" / "ended…") and two links: **Open the account** (Users, searched by e-mail) and **See their payments** (Payments, searched by e-mail). A sender with no account is told so ("probably a visitor, or a customer writing from another address").
- **Reply**: "Reply by e-mail" opens the administrator's own mail program addressed to the sender with `Re: subject`; "Copy e-mail address".
- **Internal note** (for the team only, never shown to the sender), saved with who and when; an empty note removes it.
- **Status**: Mark resolved (saves the note with it), Reopen, Mark unread. Opening an unread message marks it read. A resolved message is always read and cannot be marked unread without reopening ("resolved implies read" is what keeps the counts exact).
- **Delete** asks first and points to "Mark resolved" as the gentler option.

**Audit** (every real change, under the administrator; asking for what is already true records nothing): `message.mark_read`, `message.mark_unread`, `message.resolve` (with the operator's note), `message.reopen`, `message.note`, `message.note_cleared`, `message.delete`. The sender's name, e-mail and text are never copied into the audit log. The sender's IP hash and browser string, stored for abuse handling, are never sent to the screen.

**API** (administrator-only): `GET /api/admin/messages` (filter, search, cursor, counts; still carries the fields the Settings inbox reads) and `PATCH`/`DELETE /api/admin/messages/[id]`. Two fixes to the old routes: patching a message that does not exist used to silently create a stub document (now 404, nothing created), and DELETE of a missing message now 404s instead of auditing a delete that never happened. Counts use two plain equality counts, so no new database index; messages from before `read`/`status` existed count as unread, which is what they are.

**Also fixed (found while adding the eighth tab):** the back-office tab bar wrapped onto two rows on a desktop and stacked vertically on a phone. It now stays on one row, scrolls sideways on a phone, scrolls the current tab into view and marks it `aria-current="page"`.

## S8-03 Plans and Promo codes screens (2026-11-27)

**Plans** (`/dashboard/admin/plans`, restyled on the design tokens and shared primitives):
- Grouped by what customers see: "On the landing page" (public and active) and "Not on the landing page". Each card shows the price **in the plan's own currency**, its period, Public/Private and Active/Inactive, features, and labelled actions (Edit, Hide/Show on the landing page, Deactivate/Activate, Copy direct link, Delete with a proper confirmation).
- **Money per currency.** A plan can be in any of 13 supported currencies (previously every plan was forced to USD, and an edit silently reset a plan's currency to USD). The price is typed in major units and stored as the exact integer Stripe charges (`priceCents`, Checkout's `unit_amount`): $99.90 → 9990, **¥4,800 → 4800, not 480,000**; more decimals than the currency allows are refused as you type and on the server; a price below Stripe's usual minimum is warned about, not blocked.
- **Live preview.** The editor renders the REAL landing-page pricing section (`PricingPlans`) with the plans that are live now plus the draft, so pairing by name, the billing toggle and the "Save N %" badge appear exactly as customers will see them; warnings say when a plan will not be on the landing page, when another public plan has the same name and period (they pair by name), when the paired plan is in another currency (no saving can be shown), and when the price is below Stripe's minimum.
- **Validation** is one zod schema (`lib/shared/schemas/plans.ts` + `lib/shared/plan-input.ts`) used by the editor as you type and by the API, which answers with the fields that are wrong.
- **Cache revalidation and audit.** Every create, edit, switch and delete expires the cached public pricing and is audited under the administrator (`plan.create`, `plan.update`, `plan.toggle`, `plan.delete`, with before and after). The browser check warms the landing page's cache first, then saves, so the update proves the cache is really expired.
- Failures are no longer swallowed: a refused toggle or delete shows the server's message.

**Promo codes** (`/dashboard/admin/promo-codes`, same treatment): validation as you type with the server's own rules (code pattern, 1–3650 days, duplicate), presets, "redeemed without a rule" chips that fill the form, an On/Off switch, inline edit of length and note, delete with a confirmation, feedback for every outcome. API: zod validation, 404 for a rule that does not exist (a delete of a missing rule used to be audited), audit only for real changes, and the list now reads only the free ($0) payments instead of every payment ever made.

**Bugs found and fixed while testing (not in the task, caught by the browser walkthrough):** the price hint never showed because an empty error string hid it; clearing the code field then clicking a chip missed because a "required" message appeared on blur and pushed the chip away (it now appears only on Add); inactive rows and cards were dimmed with `opacity`, which pushed their red "Delete" text under the contrast minimum.
