# S1 evidence

## S1-01 · PAY-1 and PAY-2 reproduced against the current code (2026-11-25)

Test file: `tests/billing/current-behaviour.emu.test.ts` (run with `npm run test:emu`; Firebase
emulators, Stripe mocked, no live or test-mode Stripe calls). The two tests that assert the
*correct* behaviour are wrapped in `it.fails`; they pass today only because the defect makes them fail.
When S1-03 / S1-06 land, `it.fails` will report an error: remove the wrapper then.

| Finding | Scenario | Expected (correct) | Observed on current code |
|---|---|---|---|
| PAY-2 | Customer active for 10 more days buys a monthly plan (new session id) | expiry = old expiry + 30 days | expiry unchanged: 30 days short (`1796499234279` vs `1799091234279`); payment recorded, no time added |
| PAY-1 | Lapsed customer (expired 2 days ago) who paid for the same plan last month requests checkout | a new Checkout URL | response is `{ "alreadyPaid": true }`, no session created, account still expired |

Also pinned as passing characterisation (behaviour that is correct today and must not regress):
first purchase grants the plan period from now; replaying the same session grants nothing more;
an *expired* customer paying again gets a fresh period (PAY-2 only affects *active* customers).

Note: the PAY-1 reproduction uses a stubbed Stripe `sessions.list`; confirming how many real
customers are affected is the S2 back-fill report (PAY-7).

## S1-06 · PAY-1 fixed behind BILLING_FULFIL_V2 (2026-11-25)

`tests/billing/current-behaviour.emu.test.ts`: the PAY-1 test no longer uses `it.fails`; with
`BILLING_FULFIL_V2=1` a lapsed customer who bought the same plan last month now gets a new Checkout
URL and Stripe history is never queried. The flag-off test still pins the old `{ alreadyPaid: true }`
response, so deploying with the flag off changes nothing. `tests/billing/checkout-v2.emu.test.ts`
covers session parameters (`client_reference_id`, `metadata.env`), the idempotency key, active
customers buying again and the unchanged flag-off request.

The new checkout behaviour is gated on the same flag as the webhook and verify route on purpose:
letting active customers pay while the OLD fulfilment path is live would charge them without
extending access (PAY-2). All three switch together.
